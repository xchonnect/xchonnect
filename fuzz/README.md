# Fuzz targets

A [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz) (libFuzzer) project covering every
parser in the protocol core, the session receive path and the relay's HTTP surface. It is
a standalone crate, excluded from the main workspace, because it needs a nightly
toolchain.

## Running

```sh
rustup toolchain install nightly --profile minimal
cargo install cargo-fuzz --locked

cargo +nightly fuzz list
# Keep the committed seeds read-only: new inputs go to the first (scratch) directory.
mkdir -p /tmp/xc-corpus/envelope_decode
cargo +nightly fuzz run envelope_decode /tmp/xc-corpus/envelope_decode fuzz/corpus/envelope_decode \
  -- -max_total_time=60
```

Builds use debug assertions and overflow checks (cargo-fuzz default), so arithmetic
overflow counts as a crash. CI runs every target for 30 seconds on each push and pull
request (`fuzz` job in `.github/workflows/ci.yml`) and for ten minutes per target each
night, on a corpus that persists between runs (`.github/workflows/fuzz.yml`). How a crash
is reported and triaged: `../docs/fuzzing.md`.

A crash is written to `fuzz/artifacts/<target>/`. Minimise it with
`cargo +nightly fuzz tmin <target> <file>`, turn it into a regression unit test in
`crates/core`, then fix the core.

## Targets

| Target | Entry point | Invariants checked besides "no panic" |
|---|---|---|
| `envelope_decode` | `cbor::decode`, `Envelope::decode`, `envelope::unpad` | accepted CBOR and envelopes re-encode byte-identically; envelope field sizes match the kind; `unpad` output is a canonical prefix followed only by zeros |
| `inner_decode` | `cbor::decode` → `Inner::from_value`, `PairingReply::from_value` | canonical re-encoding; `seq` in `1..=2^53-1`; decode → encode → decode is stable |
| `uri_parse` | `PairingUri::parse` (normal and developer mode) | developer mode accepts everything normal mode accepts, with the same result; `to_uri` and universal-link forms re-parse to the same URI |
| `origin_parse` | `OriginDocument::parse` | size, name, key-count, kid syntax and uniqueness, URL rules; `not_after` is 23:59:59 UTC; key lookup honours expiry |
| `session_state` | `Session::from_bytes`, then seal / rotate / open / end on the restored state | persistence is a fixed point after one round trip; corrupted host state never panics later calls |
| `pending_requests` | `PendingRequests::from_bytes` | restored tracker has at most `MAX` entries and unique ids (as `insert` guarantees); round trip; correlation works |
| `push_reg` | `PushToken::open` with a fixed gateway key | opened tokens have a non-empty device token within the size limit and an expiry in `now..=now + MAX_LIFETIME_S` |
| `session_open` | `Session::open` on correctly sealed, fuzzer-chosen inner plaintexts (sequence of frames) | only owned mailboxes accepted; `seq` strictly increases; the same envelope never opens twice; rotation offers can be accepted; state persists |
| `relay_http` | the real `axum` router from `xchonnect_relay::app`, driven with sequences of fuzzer-built requests | no request produces 500; every response carries `no-store`, `nosniff` and `no-referrer`; JSON error bodies are exactly `{"error":"<known code>"}`; a presented capability token is never echoed in the body or a header (spec 13.5) |

`session_open` knows the session keys so the fuzzer gets past the AEAD and reaches the
state machine. Input format: one flags byte (bit 0 receiver is the dApp, bit 1 SAS
confirmed, bit 2 peer ready) followed by frames `u16be length || inner plaintext`.

`relay_http` creates a mailbox with known tokens before fuzzing, so a request can be
aimed at a real mailbox with the right token, with the wrong token, or at one that does
not exist. It runs the relay with open creation, an API key and no long polling
(`max_wait_s = 0`), and with the rate limits raised, which would otherwise hide the
handlers behind 429s. Its input format is documented at the top of
`fuzz_targets/relay_http.rs` and built by `../scripts/fuzz-seeds-relay-http.py`.

## Seed corpus

`fuzz/corpus/<target>/seed-*` are valid inputs produced by the real encoders. They are
generated (and checked to parse) by the `fuzz_seeds` unit test in `crates/core`:

```sh
XCHONNECT_FUZZ_SEEDS=$PWD/fuzz/corpus cargo test -p xchonnect-core fuzz_seeds
```

`relay_http`'s seeds are the well-formed requests of the relay API and are generated by
a script, which CI checks is in step with the committed files:

```sh
./scripts/fuzz-seeds-relay-http.py            # write fuzz/corpus/relay_http/
./scripts/fuzz-seeds-relay-http.py --check    # fail if they differ
```

Do not commit the corpus libFuzzer grows locally; only the `seed-*` files are tracked.

## Findings

Every crash a target finds, and every gap the coverage review judges worth a test, is
recorded here with what happened to it. Status values: `open`, `in progress`, `fixed`
(with the commit), `not a bug` (the harness was wrong, with what changed), `wontfix`
(with the reason).

| Id | Found by | Date | What | Status |
|---|---|---|---|---|
| F-1 | `relay_http` | 2026-10-05 | A request whose path does not percent-decode to UTF-8 (`/v1/mailboxes/not-%7F%FF.../messages`) is answered by the framework's own extractor rejection: a plain-text body, not the uniform `{"error":"<code>"}` model that `docs/spec/wire/relay-api.md` makes normative. `405 Method Not Allowed` behaves the same way. The status codes are right and the text echoes only what the client sent, so this is a spec deviation, not a disclosure. The target therefore checks the uniform model only for JSON error bodies. | open - wants a fallback layer in `crates/relay` mapping extractor rejections to `ApiError`; outside the fuzzing scope, recorded in the TASK-60 notes |
| F-2 | `relay_http` | 2026-10-05 | A `HEAD` request to a route declared with `.get(...)` is served by axum from the `GET` handler: response headers, no body. So an error response has `content-type: application/json` and an empty body. Correct HTTP; the harness wrongly demanded a parsable body. | not a bug - the target skips body checks for `HEAD` |
| F-3 | coverage review | 2026-10-05 | `crates/core/src/crypto.rs` 349-358: the redacting `Debug` impls for `HpkeSender` and `HpkeReceiver` are never executed by a test, so nothing asserts that formatting a key-bearing type cannot print key material. | open - assert the output is `HpkeSender([redacted])` and holds no key bytes |
| F-4 | coverage review | 2026-10-05 | `crates/core/src/crypto.rs` 474-475: the small-order (`is_weak`) public-key rejection in `ed25519_verify` is never taken by a test. Deliberate hardening of signature verification (T20) with no regression test. | open - add a vector with a known small-order Ed25519 key |
| F-5 | coverage review | 2026-10-05 | Minor untested paths: `MailboxId::from_slice` with a wrong length (`crypto.rs` 198-205) and `display_domain` on a label `idna` rejects (`domain.rs` 52-57, the `InvalidIdn` wallet warning). | open - low priority |

No crash found in the committed targets has so far been a real defect in the protocol
core, the relay, the gateway or wallet-kit.
