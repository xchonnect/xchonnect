# Xchonnect v1 test vectors

Known-answer tests for independent implementations of the Xchonnect protocol
([`../xchonnect-spec.md`](../xchonnect-spec.md), byte layouts in [`../wire/`](../wire/)).
An implementation that reproduces every positive vector and rejects every negative case
agrees with the reference implementation on all bytes on the wire covered here.

| File | Covers |
|---|---|
| [`pairing.json`](pairing.json) | Pairing URI, `uri_sig_input`, origin signature, HPKE PSK pairing reply, `th`, `root_0`, epoch-0 keys, SAS (spec 5.2, 6.2, 6.3) |
| [`envelope.json`](envelope.json) | Session envelopes: AAD, zero padding, XChaCha20-Poly1305, one case per bucket (spec 5.3) |
| [`rotation.json`](rotation.json) | Epoch rotation key schedule (spec 5.2 "Rotation", 9.2) |
| [`negative.json`](negative.json) | Inputs that MUST be rejected, with the expected error kind |

Like the rest of `docs/`, these files are released under CC0.

## Provenance and stability

The files are generated by the reference implementation
(`crates/core/src/vectors.rs`) from fixed inputs. CI regenerates them in memory and fails
if the committed files differ by a single byte, and separately re-derives every output
from the recorded inputs using the spec formulas; the TypeScript SDK checks them through
its WASM build (`sdk-ts/src/vectors.test.ts`). A change to any of these files is a change
to the wire format and must come with a spec change (`../PROCESS.md`). To regenerate after
an intended change:

```sh
XCHONNECT_WRITE_VECTORS=1 cargo test -p xchonnect-core --lib vectors
```

## Common conventions

Every file is a JSON object `{ "format": 1, "protocol_version": 1, "description": …,
"cases": [ … ] }`. `format` changes only if the layout of these files changes.

- **Field suffixes.** `*_hex` is lowercase hexadecimal without prefix. Fields without a
  suffix are text (`relay`, `domain`, `kid`, `uri`, …) or unsigned integers (times in unix
  seconds, lengths, counters). Base64url (RFC 4648 §5, no padding) appears only where the
  protocol itself uses it: inside `uri` and in `origin_document`.
- **Segments.** Long byte strings that consist mostly of one repeated byte are stored as
  `*_segments` instead of `*_hex`: an array whose elements are either
  `{"hex": "<literal bytes>"}` or `{"repeat": "<one byte as hex>", "count": n}`. The byte
  string is the concatenation of all segments in order. Example: `[{"hex": "a6…"},
  {"repeat": "61", "count": 899}, {"hex": "227d…"}]` is the literal prefix, 899 bytes of
  `0x61`, then the literal suffix. A reader accepts whichever of `<name>_hex` or
  `<name>_segments` is present.
- **`null`** means "absent" (e.g. no ticket, no wallet metadata).

### Where the randomness comes from

The protocol draws keys, the pairing secret, the HPKE ephemeral key and nonces from a
CSPRNG. For reproducibility every such value is given **explicitly** in the vectors
(`dsk_hex`, `pairing_secret_hex`, `ikm_e_hex`, `a_hex`, `b_hex`, `nonce_hex`), so other
implementations can simply inject them. For completeness the vectors also record the seed
the reference implementation used. Its deterministic test generator (`TestEntropy`,
`crates/core` feature `test-vectors`, never used in production) outputs the concatenation
of the blocks

```
block_i = SHA-256("xchonnect test entropy" || seed || uint64_be(i))     i = 0, 1, 2, …
```

consumed front to back. The reference implementation draws, in this order:

| Who | Draws |
|---|---|
| dApp (`DappPairing::prepare`) | `dsk` (32 bytes), then `s` (32 bytes) from `dapp_entropy_seed` |
| wallet (`WalletPairing::reply`) | `ikmE` (32 bytes) from `wallet_entropy_seed` (then a local message id that never reaches the wire) |
| rotation | `a` (32 bytes) from `a_entropy_seed`, `b` from `b_entropy_seed` |

## pairing.json

Each case runs one complete handshake (spec 6.3 steps 1–6).

**inputs**

| Field | Meaning |
|---|---|
| `dapp_entropy_seed_hex`, `wallet_entropy_seed_hex` | Seeds of the generator described above (informative) |
| `dsk_hex` | dApp pairing X25519 private key (32 bytes, raw; X25519 clamps it as usual) |
| `pairing_secret_hex` | Pairing secret `s` |
| `ikm_e_hex` | Input keying material for the wallet's HPKE ephemeral key: `(skE, pkE) = DeriveKeyPair(ikmE)` (RFC 9180 §7.1.3), exactly as in the RFC 9180 test vectors |
| `origin_seed_hex` | Ed25519 private key seed (RFC 8032) of the dApp origin key |
| `kid` | Origin key id (`i`) |
| `relay`, `domain` | `r` and `d` as decoded text |
| `pairing_mailbox_hex`, `pairing_write_token_hex` | `mbx_P` (16 bytes), `wP` (32 bytes) |
| `ticket_hex` | Sponsorship ticket `t` (32 bytes) or `null` |
| `created_at`, `lifetime_s` | URI creation time and lifetime; `x = created_at + lifetime_s` |
| `wallet_mailbox_hex`, `wallet_write_token_hex` | `mbx_W`, `wW` carried in the pairing reply |
| `wallet_name` | `meta.name` of the reply, or `null` for no `meta` |
| `reply_at` | Time at which the wallet verifies the URI and replies |

**outputs**

| Field | Definition |
|---|---|
| `dpk_hex` | `X25519(dsk, 9)` |
| `origin_pk_hex`, `origin_document` | Ed25519 public key and the `/.well-known/xchonnect.json` body the wallet verifies against |
| `expires_at` | `x` |
| `uri_sig_input_hex` | `canonical_cbor(["xchonnect pairing uri v1", r, mbx_P, wP, dpk, d, x, kid])` (`wire/pairing-uri.md`) |
| `h_uri_hex` | `SHA-256(uri_sig_input)` |
| `origin_signature_hex` | `o = Ed25519-Sign(origin_sk, uri_sig_input)` |
| `uri` | The `xchonnect:v1?…` URI (see note below) |
| `hpke_info_hex` | `"xchonnect v1 pairing" ‖ h_uri` |
| `hpke_psk_id_hex` | `"xchonnect v1 psk"` (`psk = s`) |
| `aad_pair_hex` | `"xchonnect v1 pairing reply" ‖ mbx_P` |
| `pairing_reply_plaintext_hex` | `canonical_cbor(PairingReply)` before padding |
| `pairing_reply_padded_len` | 1008: plaintext plus zero bytes, so that `ct_pair` is 1024 bytes |
| `enc_hex` | HPKE `enc` (= `pkE`) from `SetupPSKS(dpk, info, psk, psk_id)` |
| `ct_pair_hex` | `ctx.Seal(aad_pair, padded plaintext)` (first message, sequence number 0) |
| `envelope_hex` | Encoded pairing envelope `{1: 1, 2: 2, 3: enc, 4: ct_pair}` posted to `mbx_P` |
| `th_hex` | `SHA-256("xchonnect v1 transcript" ‖ h_uri ‖ enc ‖ ct_pair)` |
| `exporter_context_hex` | `"xchonnect v1 root" ‖ th` |
| `root_0_hex` | `ctx.Export(exporter_context, 32)` (identical on both sides) |
| `k_d2w_hex`, `k_w2d_hex`, `ck_0_hex` | `HKDF-Expand(root_0, "xchonnect v1 dapp->wallet" / "xchonnect v1 wallet->dapp" / "xchonnect v1 chain", 32)` |
| `sas_value`, `sas_digits`, `sas_display` | `uint64_be(HKDF-Expand(root_0, "xchonnect v1 sas", 8)) mod 1 000 000`, as six digits and as displayed (`"193 467"`) |

HPKE is RFC 9180 `mode_psk` with KEM 0x0020, KDF 0x0001, AEAD 0x0003. Intermediate HPKE
values (shared secret, key schedule) are not listed; check your HPKE library against the
RFC 9180 test vectors for that suite first.

**Note on `uri`.** The reference encoder writes parameters in the order
`r, m, w, k, s, d, x, i, o[, t]` and percent-encodes every byte of `r` outside RFC 3986
`unreserved` with uppercase hex. The grammar allows other parameter orders and
encodings, so the `uri` string is only byte-exact for encoders that make the same
choices; decoders should compare the decoded fields. Everything that is signed or hashed
(`uri_sig_input`) is independent of these choices.

## envelope.json

Each case seals one inner plaintext into a session envelope (kind 1). One case per
ciphertext bucket (1 KiB, 4 KiB, 16 KiB, 64 KiB, 256 KiB), including the boundary sizes
1009 bytes (just too large for 1 KiB), 16368 bytes (fills 16 KiB exactly) and 262128
bytes (the largest permitted plaintext). Inner plaintexts are canonical `rpc.request`
messages (spec 5.3); the large ones carry a long run of `a` characters and are given as
segments.

| Field | Meaning |
|---|---|
| `direction` | `dapp_to_wallet` (AAD byte `0x01`) or `wallet_to_dapp` (`0x02`) |
| `key_hex` | Direction key (`k_d2w` or `k_w2d`) |
| `nonce_hex` | 24-byte XChaCha20-Poly1305 nonce (`n`) |
| `recipient_mailbox_hex` | Mailbox the envelope is posted to (part of the AAD) |
| `inner_cbor_hex` / `inner_cbor_segments` | Canonical CBOR inner plaintext, unpadded |
| `inner_cbor_len`, `inner_cbor_sha256_hex` | Its length and SHA-256 (to check segment expansion) |
| `aad_hex` | `"xchonnect" ‖ u8 1 ‖ u8 1 ‖ u8 direction ‖ recipient_mailbox` (28 bytes) |
| `padded_plaintext_len` | Plaintext length after zero padding (bucket − 16) |
| `ct_len` | Ciphertext length including the 16-byte tag (the bucket) |
| `tag_hex` | Last 16 bytes of the ciphertext (Poly1305 tag) |
| `envelope_len`, `envelope_sha256_hex` | Length and SHA-256 of the encoded envelope `{1: 1, 2: 1, 3: n, 4: ct}` |
| `envelope_hex` | The full encoded envelope; present only when it is at most 4200 bytes |

For the larger buckets, compare your envelope against `envelope_len`,
`envelope_sha256_hex` and `tag_hex`.

## rotation.json

| Field | Meaning |
|---|---|
| inputs `epoch` | Current epoch `e` |
| inputs `ck_e_hex` | Chaining key of epoch `e`. Case `epoch-0-to-1` uses `ck_0` of pairing case `basic` |
| inputs `a_hex`, `b_hex` | Initiator and responder X25519 private keys (raw, clamped by X25519) |
| outputs `new_epoch` | `e + 1` |
| outputs `a_pub_hex`, `b_pub_hex` | `A = X25519(a, 9)`, `B = X25519(b, 9)` |
| outputs `dh_hex` | `X25519(a, B) = X25519(b, A)` |
| outputs `th_r_hex` | `SHA-256("xchonnect v1 rotate" ‖ uint64_be(e + 1) ‖ A ‖ B)` |
| outputs `prk_hex` | `HKDF-Extract(salt = ck_e, ikm = dh)` |
| outputs `root_hex` | `root_{e+1} = HKDF-Expand(prk, "xchonnect v1 root" ‖ th_r, 32)` |
| outputs `k_d2w_hex`, `k_w2d_hex`, `ck_hex` | Keys of epoch `e + 1`, derived from `root_{e+1}` as for epoch 0 |

## negative.json

Each case has `id`, `description`, `check` (the operation to run), operation-specific
inputs and `expected_error`. The operation MUST fail. `expected_error` is the reference
implementation's error kind; implementations need not use the same names, but each case
violates exactly one rule, so the failure should be of the same nature (a non-canonical
inner plaintext inside a correctly encrypted envelope is a CBOR error, not a decryption
failure).

| `check` | Inputs | Operation |
|---|---|---|
| `verify_uri` | `uri`, `origin_document`, `now` | Wallet steps 1–4 of `wire/pairing-uri.md`: parse, check expiry at `now`, select `kid`, verify `o` |
| `dapp_on_reply` | `pairing_case`, `now`, `envelope_hex` | Build the dApp of the named `pairing.json` case from its inputs, then process the envelope as a pairing reply at `now` |
| `decode_envelope` | `envelope_hex` / `envelope_segments` | Decode and validate the outer envelope as a relay does (size limit, canonical CBOR, CDDL) |
| `open_session` | `key_hex`, `direction`, `recipient_mailbox_hex`, `envelope_hex` | Decode, decrypt, check padding and decode the inner CBOR |
| `seal_session` | `key_hex`, `nonce_hex`, `direction`, `recipient_mailbox_hex`, `inner_cbor_*` | Pad and encrypt (sender side) |
| `session_receive` | `root_0_hex` (and the derived `key_hex`), `direction`, `recipient_mailbox_hex`, `last_accepted_seq`, `now`, `envelope_hex`, `inner_cbor_hex` | A `role` session (always `wallet`, receiving dApp → wallet) that already accepted `last_accepted_seq` receives the envelope at `now`. The envelope decrypts to `inner_cbor_hex`; the spec 5.3 receive rules must reject it |

| `expected_error` | Meaning |
|---|---|
| `bad_signature` | Origin signature does not verify |
| `invalid_origin` | Origin document does not authorise the key (e.g. unknown `kid`) |
| `uri_expired` | `x` in the past, or more than 300 s + 60 s skew in the future |
| `decrypt` | AEAD or HPKE authentication failed (wrong key, AAD or tampered data) |
| `cbor` | Not canonical CBOR (spec 5.4) |
| `malformed` | Canonical CBOR that violates the CDDL or padding rule (wrong lengths, unknown outer key, non-zero padding) |
| `unsupported_version` | Envelope `v` is not 1 |
| `too_large` | Envelope above 262400 bytes, or plaintext + tag above 256 KiB |
| `replay` | `seq` not greater than the last accepted `seq` |
| `expired`, `lifetime_too_long`, `clock_skew` | `exp < now`, `exp − iat > 7 days`, `iat > now + 300 s` |

Covered: wrong origin signature (other key, changed domain, flipped bit), unknown `kid`,
expired URI and over-long URI lifetime, tampered and late pairing replies, unknown versions
(`v` = 0, 2), oversized envelope and plaintext, ciphertext not a bucket size, wrong nonce
length, unknown outer key, non-canonical CBOR (non-shortest integer and length, indefinite
map and byte string, unsorted and duplicate keys, trailing bytes, tag, float — in the outer
envelope, and unsorted keys / non-shortest integer inside a correctly encrypted inner
plaintext), tampered AAD (wrong direction, wrong recipient mailbox), tampered tag,
non-zero padding (first and last padding byte), replayed and reordered `seq`, expired
message, over-long lifetime and future `iat`.
