# Specification changelog

All normative changes to `xchonnect-spec.md` are recorded here. Versions are tagged
`spec-vX.Y` in git.

## Unreleased (v0.2)

- **14 (security audit L2, editorial):** a data-inventory row for the agent plugin's IP address: the reference plugin reaches the relay without OHTTP, so the relay operator can see the agent machine's IP at the network layer for the pairing's life (not stored by the relay). **No normative or wire change.** T9.

- **New 9.4 (TASK-80, draft); 11.1 item 4, 13.3 (T22), 13.4, 13.6, 14:** agent sessions. An agent pairs like a dApp; a wallet that supports agents keeps rules for the pairing and answers what they allow without a prompt, refusing the rest before anyone is asked with 4001/4029 and one `data.reason` from a closed list (`paused`, `expired`, `outside_hours`, `action_not_allowed`, `asset_not_allowed`, `price_out_of_band`, `limit_per_trade`, `limit_per_period`), checked in that order. The rules fail closed: an agent may only take or create one-for-one offers of allowed fungible assets, every pair needs a price band (compared exactly), an asset without a limit has a limit of 0, the network fee counts as XCH leaving, an offer must carry `expiresAt` within the rules' expiry and `maxOfferSeconds`, and what an offer gives stays held until its coins are spent on chain or it expires (a cancel is on chain and releases nothing until confirmed). Cancelling the agent's own offers is never refused by the rules. Periods are UTC days and weeks from Monday. `xchonnect_getAgentRules` reads the rules and what is left; a wallet without agents answers 4004. 11.1 item 4 and invariant 13.4 #3 gain the agent exception (the user's authentication is taken when the rules are turned on or loosened); new threat T22; a 13.6 limitation; two rows in the data inventory. Vectors: `vectors/agent.json`. **No wire format change** (method layer only). T1, T8, T22.

- **9.1, 9.3, 11.1, 11.1.1, 11.2, 13.6 (TASK-78, round-5 audit before release):** 11.2: a request is **multi-party**, and needs binding, when it asks for a partial signature, carries another party's signature, or spends a coin that is neither the user's nor created by a spend of the request (previously only the first two), so a dApp cannot drop another party's spends and use the user's signature alone. A **user spend** is every spend the wallet signs (an `AGG_SIG_*` naming one of its keys), recognised or not; a multi-party request containing one the wallet does not recognise is refused (new 4001 reason `"unknown_partial"`). A request is **sealed** only if, in addition, the user's spends reserve exactly the fee the wallet chose and, with more than one user spend, every user spend requires every other through the sealed links (co-required): spends that were each bound but not tied together could be separated once one coin was spent and its record forgotten. The record of sealed signatures is per bundle: a bundle's pairs are kept until every coin the wallet signed for in it is spent on chain; keeping entries for good is RECOMMENDED. The reference kit's `host_checks` checks a host's storage and request lock (the conformance suite cannot reach a sealed request). 11.1 item 3: a spend the wallet signs inside an unknown contract is a user spend, its coin counts as leaving the user and its outputs are shown as unaccounted, never received. 11.1 item 5, 9.3: options leaving the user count against a limit of their own, a number of options per request and per day, enforced by default (reference: one and five; new 4029 reasons `"options_per_request"`, `"options_per_day"`; `"per_request"` and `"per_day"` named). 11.1.1: a sealed exercise's fee credit is at most the fee the wallet chose; a melted option's mojos count as one per option. 13.6: two limitations added. **No wire format change.** T1, T2, T13, T14.

- **11.2 (TASK-78, round-4 audit of the record of signatures before release):** three obligations on a wallet that treats requests as sealed. It MUST process its coin-signing requests (`signCoinSpends`, `xchonnect_submitCoinSpends`, `signMessage`, and every wallet-built bundle it signs or broadcasts, from any dApp or its own interface) one at a time against the record, from the moment a request reads it (the reference kit reads it before the approval prompt) until what the request recorded is stored: otherwise a request opened before a sealed bundle was recorded and approved after would sign one of its messages again. "Spent on chain" means spent in the wallet's own verified sync at its reorg-safe depth (RECOMMENDED at least 6 blocks), never on an unverified peer report; keeping entries for good is correct. Every signature over a spend of the wallet's coins made outside the kit (its own interface, offers, other dApp protocols) MUST be recorded into the released coins before it leaves the wallet. The reference kit now records a `signCoinSpends` answer's coins itself before returning the signature (4000 `"record_failed"`, no signature, when the host cannot store them). **No wire format change.** T2.

- **9.1, 11.1.1, 11.2 (TASK-78, audit of the sealed rule below before release):** the wallet's record of a sealed bundle is per signature, not per coin. 11.2: *coins in flight* (refused in every request until any coin of the bundle was spent on chain) is replaced by **sealed signatures**: the exact `(public key, message)` pairs the wallet signed for each of its coins in a sealed bundle, recorded before the bundle leaves the wallet (a refused bundle counts) and kept until that coin is spent on chain. The wallet never signs a recorded pair again, in any request (new 4001 reason `"sealed_signature"`, replacing `"coin_in_flight"`); a sealed bundle is sent again by rebroadcasting it. Clearing the record when another coin of the bundle was spent let the public aggregate be split with one more signature over the same spend; a different spend of the coin is no longer refused, so a bundle that expired or was refused locks nothing. The reference kit reports what to record through `Broadcaster::record` (new 4000 reason `"record_failed"` when the host cannot store it). 11.1.1: the fee credited in a sealed request MUST be one the wallet chose, never a figure from the dApp's parameters.

- **9.1, 11.1 item 2, 11.1.1, 11.2 (TASK-78, final audit of the rules below before release):** binding through a link between two of the user's spends could be defeated, and Sage's own bundles were refused. 11.2 now distinguishes **released** requests (any signature or the signed bundle goes back to the dApp or is handed on: every `signCoinSpends`, every dApp-built bundle, a signed offer such as a loan request) from **sealed** ones (wallet-built, broadcast by the wallet, which returns only `{ transactionId, status }`; no user coin with a signature outside the wallet; every user spend signed with `AGG_SIG_ME` only). Released: only direct binding counts, and every user spend MUST assert every settlement announcement any user spend asserts; a coin announcement between user spends no longer binds (a dApp holding another signed spend of the announcing coin with the same announcement, and the announcing spend's own signature, could swap them), nor does `ASSERT_CONCURRENT_SPEND`. Sealed: the user's spends are included together, so `ASSERT_CONCURRENT_SPEND` of another user spend's coin and coin announcements between user spends link them (Sage's `Relation::AssertConcurrent` bundles pass unchanged). A wallet that treats requests as sealed MUST keep a record of its coins with signatures outside it (released coins) and of the coins of sealed bundles in flight, and MUST refuse any request spending a coin in flight (new 4001 reason `"coin_in_flight"`). 11.1.1: a launch is guaranteed, when released, only if the spend creating the collateral asserts the launcher's announcement, and when sealed through the sealed links; an exercise is co-required, when released, only if every user spend asserts every payment the user's spends assert, with each user spend counted in the cover only when it loses, and when sealed if the spends are linked, with the fee the wallet reserved credited up to the bundle's fee. 11.2 also says how a wallet builds a loan request (released): every user spend asserts the principal, the collateral's spend asserts the launch. 9.1: `xchonnect_submitCoinSpends` is released; wallet-built methods may be sealed; `loan.request` needs direct links. 11.1 item 2: the signed-conditions guarantee is the standard puzzle's; a note on coin-bound variants other than `AGG_SIG_ME`. **No wire format change**; two new `multiparty.json` cases (two coins each bound; two coins linked through an announcement, refused). These rules were never released: they amend the unreleased entries below. T2.

- **11.1 item 2, 9.1 (signing policy):** the signature scope is narrowed, whatever the user allowed. A wallet signs an `AGG_SIG_ME` for its keys only over the tree hash of a quoted program `(q . conditions)` the spend's solution reveals, and at most one such message per key and spend; otherwise it refuses with the new 4001 reason `"unsigned_conditions"`, with no override. This makes the conditions the wallet simulated the only ones its signature authorises, for a standard puzzle anywhere in a spend (bare, in a CAT, as the owner of an option, as an option's collateral path). An `AGG_SIG_UNSAFE` whose message ends with the additional data of a coin-bound `AGG_SIG_*` variant (this network, mainnet or testnet11), or is 32 bytes long (a `signMessage` digest), is refused even where the user allowed `AGG_SIG_UNSAFE`. A request spending one coin twice is refused (4000). **No wire format change**; one new error reason; the vectors are unchanged. dApps that build the user's spends with a delegated puzzle that is not quoted are refused. T1.

- **9.1, 11.1.1, 11.2 (TASK-78, re-audit of the rules below before release):** the amended rules had holes of their own. 11.2: `ASSERT_CONCURRENT_SPEND` (and `ASSERT_CONCURRENT_PUZZLE`) no longer bind or link user spends: they name a coin, not a spend, so any later spend of that coin the user signs satisfied them and a dApp could attach the user's earlier signed spend to it; only a coin announcement that another user spend of the request creates in conditions the user signed links two spends (puzzle announcements, ring announcements and other puzzles' announcements do not). Only an odd payment of a settlement-held option carries the option; an even payment is XCH. 11.1.1 item 1: the requirement between the funding spend and the asserting spend follows (coin announcements only). Exercise: each exercised option is credited its own strike only when the strike is in the collateral's asset and never more than its own collateral (an option whose strike exceeds its collateral used to offset another's collateral), and the reserved fee only up to the XCH the user's own spends put into the bundle (released collateral used to become the "user's" fee); an exercise that loses value in the collateral's own asset is refused. New item 7: a request in which the user's coins fund the collateral of a mint under another creator that expires within an hour of the wallet's time MUST be refused (new 4001 reason `"option_expires"`), and the mint kinds of 9.1 hold only for an option that expires later than that. 9.1 and Display: the collateral of an option the user holds under another creator is a payment to that creator in `recipients`. Consequence: bundles whose spends are linked only by `ASSERT_CONCURRENT_SPEND` (the Wallet SDK's `Relation::AssertConcurrent`, as Sage builds them) are refused again for exercises and for mints whose collateral and launch come from different coins, until the wallet links them with coin announcements; an XCH-collateral exercise that pays its fee out of collateral absorbed into the wallet's change is refused. **No wire format change**; the multi-party vectors are unchanged. Never released: amends the unreleased entries below. T1, T2.

- **9.1, 11.1.1, 11.2 (TASK-78, security audit and review of the option rules before release):** the option rules below were too weak or refused real wallets' bundles. 11.1.1 item 1: a launch is **guaranteed** only if the user's own spends create the collateral, a user spend asserts the launcher's announcement, those two spends require each other, and the eve's outputs are fixed (a quoted inner puzzle, or the user's own puzzle, as Sage mints); a counterparty's funding spend can be swapped for one that keeps the money, so collateral funded by another party is never guaranteed. The eve MUST be 1 mojo and the launcher at most 1 (value hidden in a larger launcher). New item 6: revocable-CAT collateral and strikes are not shown. Display: a mint's collateral and launcher are a payment to the option's owner unless the user holds the guaranteed option; even outputs of an option singleton count as XCH sent; a clawback returns collateral to the balance; the eve of a mint is not something the user held. Exercise: the old rule (every user spend bound, bound payments to the user covering the collateral) is replaced: the user's spends MUST require one another and the user's guaranteed outcome in each collateral asset MUST reach the collateral less the strike and the reserved fee, with every other payment counted as spent (a refund of the user's own money covered the collateral before, while the released collateral went elsewhere) and a clawback in the same request counted as nothing, and with collateral absorbed into the user's own signed change counted (the Wallet SDK's bundles were all refused before). 9.1: `option:<launcher id>` joins the `assetId` grammar; `option.mint`, `loan.request` and `loan.take` require a guaranteed launch (so `loan.take` never holds); a verified kind says only that the request contains the effect; the outputs-are-not-payments rule is narrowed as above. 11.2: `ASSERT_CONCURRENT_SPEND` of a bound user spend binds transitively; a CAT's ring announcements (`0xcb…`) no longer do (the user's signature does not cover them); an option singleton owned by the settlement puzzle announces its payments like a settlement coin. **No wire format change**; the multi-party vectors are unchanged. These rules were never released: they amend the unreleased entry below. T1 (value to a stranger shown as a lock), T2 (exercise and mint binding).

- **9.1, new 11.1.1 (TASK-78):** option contracts. 11.1.1 says when a wallet may show a spend as part of a Chia option (mint, transfer, exercise, clawback): every commitment verified within the request (launcher and eve lineage, the collateral coin created in the same request rebuilding its puzzle hash and the option's committed exercise from the launcher's hint and metadata, the strike as a settlement payment with the launcher id as nonce, the option's own `ASSERT_MY_*` lineage check), else it stays an unknown contract. Collateral is shown as locked under the option until expiry and claimable by its creator, not as a payment; an exercise by the user MUST be bound to the settlement payment that gives the user the collateral (new 4001 reason `"unbound_exercise"`); limits count locked collateral and the strike paid. 9.1: six verified intent kinds (`option.mint`, `option.transfer`, `option.exercise`, `option.clawback`, `loan.request`, `loan.take`) that the wallet checks against those effects and refuses on mismatch; any other `kind` stays a description; option-mint outputs are not `recipients`. **No wire format change:** messages, `wire/envelope.cddl` and the vectors are untouched; a dApp that used one of the six values as a free label now has it checked. T1 (a mint no longer reads as a payment to a stranger, an option no longer as an unknown contract), T2 (exercise binding).

- **7.3, 7.3.1 rule 5, 7.3.2, 8.2, new 8.4, 12:** delivery through suspended pages and apps. 7.3: the APNs payload SHOULD carry `content-available: 1` next to the alert so iOS wakes the wallet in the background, also on a locked phone; push lifetimes SHOULD be at least 600 s. 7.3.1 rule 5 and 7.3.2: a wake-up inside the 10 s window SHOULD be deferred to its end instead of dropped (relay: only if messages still wait; at most one pending per mailbox or device; the hourly cap counts it), so the rates are unchanged. 8.2: a return URL opens the browser, not a home-screen web app; the dApp MUST NOT depend on it and re-polls when visible. 8.4 (new): client deadlines for every relay request (long poll: `wait` + grace, RECOMMENDED 10 s; other requests RECOMMENDED 15 s); resumption on visibility, `pageshow`, focus and `online` (MUST abort the poll in flight and poll again); `Retry-After` MUST be honoured; acknowledge only what was persisted or is invalid; keep-alive long poll while visible and polling after `session.ready` (SHOULD); wallets SHOULD answer prompt-free reads without queueing them behind a prompt. 12: the visibility rule points to 8.4. **No wire format change.** T11 (payload still a pure function of the configuration), T21 (wake-up rates unchanged).

- **8.1, 8.3, 9.1, 11.1 item 4, 17 (TASK-75):** wallet-side execution written down, as implemented in `xchonnect-wallet-kit` (`handlers::submit`, `intent.rs`) and the Klimper wallet since TASK-74. 8.3: the wallet that signs a spend it can complete alone MUST broadcast it and return the transaction id; a dApp MUST NOT submit a bundle it obtained over Xchonnect, and `signCoinSpends` is for a contribution another party completes; before broadcasting, the aggregate MUST satisfy every requirement of the bundle, and the loss counts against limits only once the transaction left the wallet. 9.1: `xchonnect_submitCoinSpends { coinSpends, aggregatedSignature?, intent? }` → `{ transactionId, status }` joins the required methods; the wallet-built `chia_*` methods (`chia_send { address, amount, fee?, assetId?, memos? }`) are optional and go through the same checks and the same single prompt; the `Intent` schema (`kind`, `recipients`, `fee`, `netChange`) is a set of claims the wallet verifies against its simulation and refuses on mismatch before the user sees anything (4001 `intent_mismatch`, 4000 `invalid_intent`; also 4000 `signature_incomplete`, `broadcast_failed`). 11.1 item 4: one decision and one fresh authentication per request, covering every signature, instead of one per signature. 17: the three method namespaces (CHIP-0002, `chia_*` with Sage's WalletConnect shapes, `xchonnect_*`). **No wire format change:** every message is an `rpc.request`/`rpc.response` as before; `wire/envelope.cddl` and the vectors are untouched. T4, T5, T7 (the dApp no longer reads coins or pushes transactions, so no third party sees address, IP and transaction together).

- **10, 14, 15, 16, 18, 19 (editorial):** Sections 15 (hosted relay product) and 18 (milestones) are emptied and keep only their numbers, so that later sections keep theirs; the open questions OQ-1, OQ-5 and OQ-9 are dropped. None of this was part of the protocol. Three informative sentences that referred to hosted "tiers" (in 10, 14 and 16) now say "hosted relays". **No normative change.**

- **9.1, wire/envelope.cddl:** two new method-layer messages and one error code. `rpc.cancel { request_id }` lets either side withdraw a request the user has not decided; the wallet removes it from its queue and answers 4102 `RequestCancelledError`. `rpc.status { request_id, state, tx_id? }` lets a wallet report `shown`, `approved` and `broadcast` (with the transaction id) while the user decides and the wallet sends. Both are additive: an implementation that does not know them treats them as unknown message types, and the request still ends with its `rpc.response`.

- **Header, 7, 8, 10–13, 15, 18 (editorial, public release):** the spec no longer reads as an internal product document. The header states the version as 0.2 (draft) and the audit status; requirements written as "Klimper MUST" or "the Pengui SDK MUST" now say "the wallet" and "dApp SDKs", and section titles drop product names. Sections 15 (hosted relay product) and 18 (milestones) are marked informative. **No normative change:** every requirement applies to the same party as before, now named by role.

- **6.3, 9.3 (editorial):** the handshake sequence diagram was wrong. It drew the wallet's final message as `session.ready { meta, permissions }`, but no version of this protocol has ever carried permissions in that body: `SessionReady` in `wire/envelope.cddl` has only the optional `meta`, and the declaration has its own message `session.permissions` (`SessionPermissions`, defined in the same grammar and in 9.3). The diagram now shows `session.ready { meta }` followed by its own `session.permissions` arrow, and 9.3 says in prose that the declaration is a message of its own, optional, and may be re-sent when the grant changes. **No wire format change:** the grammar, the message table in 9.2, the signature inputs and the test vectors are untouched, and the three implementations (`crates/core`, `bindings/*`, `sdk-ts`) already agreed with the grammar rather than with the picture. Only the picture and the prose around it moved.

- **6.2, 7.3, 8.2, wire/pairing-uri.md (editorial):** the illustrative examples now use the RFC 2606 placeholder domains `dapp.example` and `wallet.example` instead of `pengui.xyz`, `klimper.app` and `push.klimper.app`, which name hosts the project does not control. No normative requirement, grammar, signature input or test vector changes; the entry is here because 6.1 requires the origin document to come from the exact domain claimed and `return_url` to share that authority byte for byte, so the old examples contradicted the rules they illustrate, and because downstream implementers copy these strings verbatim. The published vectors already use `dapp.example` and `relay.example`, and their `d=` bytes are signed and were left untouched.

- **wire/xchonnect.schema.json (review):** the origin document's `return_url` same-domain rule made precise and mandatory: its authority MUST be byte-identical to the pairing URI's `d` — not a subdomain, no port, no userinfo, no trailing dot, written in the same lowercase A-label form — and a wallet MUST reject the whole document otherwise. `icon` carries no such rule. Previously the rule existed only as prose in the schema's description, so every wallet had to re-implement the host check and a dApp whose origin key leaked could point the user at another host (T18, and it undercut the verified-domain display T3 relies on).

- **wire/relay-api.md (review):** the uniform error model is stated to cover *every* error response, including the ones a relay's HTTP framework raises before a handler runs, with `application/problem+json` for the OHTTP key mismatch (RFC 9458 §5.3) as the only exception. New row `405 method_not_allowed` for a path that exists but not for the request's method, which carries `Allow`. `404 not_found` also covers an unknown path.

- **10.6, T10, 13.6 (TASK-70):** node requests (`push_tx`) are sent through OHTTP to a gateway operated by the node operator, reached through the same independent OHTTP relay; relays MUST NOT offer a forwarding endpoint for node requests, because the relay would otherwise see plaintext spend bundles (T7, T10, 4.1). Nodes without a pinned gateway configuration are submitted to directly and the client must report that per node. Node requests carry no relay credential, mailbox id or session material.

- **10.5, 10.2, T9, 13.6 (TASK-69):** inner binary HTTP requests and responses are padded with zero bytes (RFC 9292 §3.8) to size buckets — powers of two from 2 KiB to 256 KiB, then multiples of 256 KiB up to 16 MiB — so the OHTTP relay cannot infer the endpoint or the number of envelopes in a fetch from the encapsulated length. The 2 KiB floor makes every control request, a one-envelope post and an empty or one-envelope fetch response identical in length. Recipients ignore padding and must not reject unpadded messages. The OHTTP relay body-size requirements in 10.2 are restated for padded messages (528 KiB requests, 12 MiB responses).

- **10.4, 16, wire/relay-api.md (TASK-51):** gateway replay handling specified: refuse an encapsulated request whose HPKE `enc` was accepted within a window of at least 600 s, record `enc` only after successful decryption (so an `enc`-reusing forgery cannot block the genuine request), answer byte-identically to a malformed encapsulation and never reach the inner endpoint, keep replay state in memory, per node and bounded, and never in shared storage. Undetected repeats are explicitly allowed because every endpoint tolerates them. Operators publish the window and the bound. T9.

- **7.3.2, 7.3.3, wire/envelope.cddl (TASK-48):** encrypted notification preview specified: `NotificationPreview` sealed with XChaCha20-Poly1305 under `HKDF-Expand(mailbox_hint_key, "xchonnect v1 preview key")`, zero-padded to a single 168-byte wire size so the length leaks nothing, carried opaquely by the gateway in the APNs `xcp` key or the FCM `data.xcp` member, with a 600 s expiry, an opt-in-only detail line that rejects control characters and bidi overrides, and a mandatory fallback to the generic alert. 7.3.2 also made the gateway's forget path normative: an invalidated device token is discarded with its rate-limit state and never reported in the (uniform) wake response. T11, T12.

- **wire/relay-api.md, 10 (TASK-51):** OHTTP gateway resource defined: key configurations at `/.well-known/ohttp-keys` (newest first, previous key kept during rotation, X25519 with AES-128-GCM and ChaCha20-Poly1305), gateway at `POST /.well-known/ohttp-gateway`, inner header allowlist, RFC 9458 `ohttp-key` problem for unknown keys, per-node replay window. T9.

- **11.2 (TASK-56):** binding made precise: settlement-payment puzzle announcements (direct) and coin announcements of bound user spends (transitive) bind; other announcements do not; every user spend must be bound.

- **7.4 (review):** spent proof-of-work challenges are recorded in storage shared by all relay nodes; rate limits are charged after verification and before spending.

- **wire/relay-api.md (TASK-36 review):** `Cache-Control: no-store` and CORS behaviour made normative; `413 too_large` for envelopes above `max_envelope_bytes`; `403 api_key_invalid` for ticket requests without a valid key; rate limits checked before consuming tickets or proof-of-work.

- **5.1, 6.3, wire/pairing-uri.md (TASK-24 review):** clarifications found while writing test vectors: pairing replies must be one canonical `PairingReply` plus zero padding; the dApp applies no clock skew to `x`; error kind for non-v1 structures is unspecified (rejection is mandatory); URI strings are not unique and are compared by decoded fields, with a recommended canonical encoder order.

- **9.2.1 (TASK-37):** the rotation responder keeps its previous mailbox until a message from the initiator arrives on its new mailbox; the initiator sends `session.ping` right after switching. Found by the interop test: retiring early made the initiator post to a deleted mailbox.

- **9.2.1 (TASK-22):** rotation procedure made explicit: accept sent under the old epoch to the old mailbox, drain order, `seq` continuity, deterministic resolution of concurrent offers; `session.pong` added as the answer to `session.ping`.

- **wire/, 6.1, 6.2, 7.2 (TASK-9):** normative wire definitions added: CDDL for all CBOR structures, pairing URI ABNF and byte-exact signature input (now a canonical CBOR array; adds `m` mailbox id, `i` key id, optional `t`; `s` not signed), origin document JSON Schema with fetch rules, full relay API with error model, token hashing and limits. Pairing reply padded to a 1024-byte ciphertext. New endpoints `GET /v1/info`, `POST /v1/challenge`, `POST /v1/tickets`; message bodies carry the envelope as base64url `env`.

- **5.4, 7.4, 7.5, 19 (TASK-8):** canonical CBOR profile specified; stateless proof-of-work for keyless mailbox creation; single-use sponsorship tickets (URI param `t`) so wallets can create mailboxes billed to the dApp customer; OQ-2, OQ-3, OQ-6 decided; remaining open questions have owners or are out of scope for v1.

- **9.1, Appendix A, OQ-4 (TASK-11):** method layer aligned with CHIP-0002 Final: bare method names with `chip0002_` aliases, required set adds `chainId`, params/result carried as JSON text, hex/amount encodings fixed, `partialSign` semantics stated, CHIP-0002 error codes plus 4100/4101, optional `rpc.received` receipt. Informative appendix of Sage/Goby deviations.

- **12.1 (TASK-10):** browser session storage requirements (IndexedDB, optional non-extractable WebCrypto wrapping, no localStorage), logout and lifetime rules, cross-tab serialisation of `seq`, explicit XSS residual risk.

- **10.1–10.3, 13.6 (TASK-7):** OHTTP clients use bounded waits advertised as `max_wait_ohttp_s` (default 0) with a defined polling schedule; minimum requirements on OHTTP relays (body size, CORS, timeouts, no forwarding headers); TLS-terminating edges must be disclosed in the data inventory.

- **7.3.1, 7.3.2, T21 (TASK-6):** mandatory relay egress rules for wake-ups (HTTPS, globally routable destinations validated after resolution and pinned, no redirects, timeouts), gateway policy modes `allowlist`/`open` published via `GET /v1/info`, wake coalescing; sealed token gains `exp`, gateways rate-limit per device token. New threat T21.

- **6.2–6.4, T3 (TASK-5):** pairing uses a single-use pairing mailbox P that the dApp deletes as soon as the first valid reply is accepted; the session mailbox D is created afterwards and sent in `session.confirm`. Losing wallets get `not_found` or time out and must warn the user. The dApp must obtain explicit user SAS confirmation and `session.ready` before activating. Timeouts specified.

- **5.2, 6.3, 13.4.1 (TASK-4):** new key schedule. The dApp pairing key is used only as the HPKE recipient key (previously reused in a raw X25519); the wallet's key contribution is the HPKE `enc`. `root_0` comes from the HPKE exporter over a byte-exact transcript hash; direction keys, chaining key and SAS are domain-separated HKDF-Expand outputs. SAS reduction specified. Rotation key schedule specified. Cryptographic properties and non-goals stated.

- **5, 5.3 (TASK-3):** session AEAD changed from ChaCha20-Poly1305 with `seq`-derived nonces to XChaCha20-Poly1305 with a random 192-bit nonce carried in the outer envelope (`n`). Outer envelope gains `kind`; AAD made byte-exact and includes `kind`. Padding now pads the *ciphertext* to exact bucket sizes. `seq` is used only for replay/ordering; senders that lose state must re-pair. T5/T20 updated.
